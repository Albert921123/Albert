# Generate Daily Industry Brief

Produce a concise, source-linked Chinese morning brief from the user's selected sections. Deliver the brief as a complete `.html` artifact, not Markdown.

## Full-package reading gate — mandatory before any execution

An Agent must read the **entire installed skill bundle**, not only `SKILL.md`, before it opens a selector, searches, fetches a page, uses a cached candidate, writes HTML, validates an artifact, creates/updates a schedule, or answers that a run has begun. This is a hard precondition for every invocation, including a bare `调用`, a scheduled heartbeat, a catch-up, a layout repair and a settings edit.

1. First run `python scripts/verify_install.py` against the actual installed directory. If it fails, stop; do not execute a partial bundle.
2. Run `python scripts/create_reading_receipt.py --skill-dir <installed-skill-dir> --run-id <unique-run-id> --output <workspace>/.zhixun-reading-<unique-run-id>.json` only after reading every textual installation file listed by that receipt to EOF: root instructions/metadata, `agents/`, every `assets/` template, every `entrypoints/` file, every `references/` file, and every executable source/wrapper in `scripts/`. Binary caches, `__pycache__` and workspace/runtime state under `.zhixun-state` are excluded because they are not installation content; no other installation content may be skipped.
3. Immediately run `python scripts/verify_reading_receipt.py --skill-dir <installed-skill-dir> --run-id <unique-run-id> --receipt <receipt-path>`. Record the verified receipt path and file count under `run.full_package_reading` in the retrieval ledger.
4. If the receipt is absent, stale, mismatches a file hash, or the Agent cannot read a file to EOF, stop and report `技能包未完整读取，未开始执行`. Do not substitute a summary, a directory listing, a previous run's receipt, or a claim that “the relevant files were read.” A new invocation needs a new run ID and a new receipt after the full package is read.
5. The completion gate applies to every selected board. Reading a source-map excerpt, checking one or two boards, or reading only the template never authorizes partial execution. Do not start board retrieval until the full-package receipt has passed.

## Non-negotiable live-run completion gate

When a live network route is working, create `retrieval-ledger-YYYY-MM-DD.json` before writing any report card and finish the retrieval passes for **every** selected row. Do not emit an early “补发版”、preview, or baseline-filled HTML merely because a few convenient candidates were verified. A live row may end only as `complete`、`observed`、`expanded`、`business-observation` or evidence-backed `checked-empty`; `baseline` is offline-only and is invalid whenever the run audit records an available live route. If every permitted retrieval route is genuinely unavailable or returns no openable, time-verifiable original record, the Agent must still close every row as `limited` with the actual shared constraint and render one complete standalone **检索受限版 HTML** in the same invocation. It preserves the application shell, navigation, search and seven-column audit, contains no invented news or source link, and is delivered without a success marker.

For every live, catch-up, retry, or scheduled generation, read [`references/execution-runner.md`](references/execution-runner.md) and create a durable run state with `scripts/run_state.py` immediately after the full-package receipt passes. Advance its phases only after the corresponding work actually completes. A running state file is evidence of the current run, not a claim that work continues in the background after the Agent turn ends. In a user-requested generation, after each checkpoint continue to the next unfinished planned row in the **same active turn**; a checkpoint, candidate discovery, or a partial ledger is not a permitted stopping point. A route failure, login requirement, or unavailable capability does not by itself permit a text-only stop: first exhaust the configured routes, close every selected row, and deliver the full 检索受限版 HTML. Use `block` only for a real turn interruption or execution ceiling before all rows can be closed, with exact pending rows and a resume action. On the next invocation, run `scripts/run_state.py resume --state-file <path>` before continuing from that same state; do not create a fresh state merely to bypass a block. Rediscover/reverify any candidate whose live time window has expired. A human-readable delivery is permitted only after the paired ledger and HTML both pass their validators and the state helper records all four gates as passed, except that the explicitly labeled 检索受限版 may be delivered after its structural HTML/audit checks pass and must never receive a success marker. The one-event/one-section assignment rule below remains mandatory.

### Code-signed formal delivery — mandatory

For every formal live, catch-up, retry or scheduled report, `scripts/run_pipeline.py` is the **single Agent-facing supervisor** from initialization through delivery. Do not call lower-level `run_brief.py` commands directly to bypass a phase. Host-native tools still perform search and original-page inspection, but a hand-written `build_*.py`, copied prior report, `validate_html.py` alone, or an Agent's own completion statement is never formal delivery evidence.

1. Run `run_pipeline.py init --plan <plan> --profiles <profiles> --reading-receipt <receipt> --work-state <work-state> --output <pipeline-state>`. The supervisor verifies the current full-package reading receipt and binds the plan and profiles before returning the first required host-search action.
2. Execute only the action returned by `run_pipeline.py next`. Persist every search through `record-query --raw-results <query-receipt.json>` and every inclusion/exclusion through `record-decision`; close a row only through `close-section`.
3. After every planned row closes, run `seal-retrieval`, then `authorize-render --ledger <ledger> --model <brief-model> --registry references/source-registry.json`. Authorization is refused unless the raw query receipts, work state, ledger, source claims, time windows and editorial model all reconcile.
4. Run `run_pipeline.py render` to build the HTML deterministically from the authorized model and locked template. Do not use an ad-hoc renderer.
5. Run `run_pipeline.py finalize`. It reruns the ledger, source registry, editorial model, time, HTML, editorial and template gates and writes the hash-bound `zhixun-formal-delivery-receipt-<run-id>.json`.
6. Call a report formally delivered only when the receipt says `all_gates_passed: true` and its artifact/ledger/model hashes match the linked files. Without it, report `未正式交付`.

`target_card_count` is a discovery/comparison target, not an output quota. Keep one genuinely qualifying story when only one exists. A row below target may close only when `candidate_pool_exhausted: true`, `additional_discovery_completed: true`, all four lane records are present, every discovered candidate has an included/excluded decision, and `below_target_reason` specifically reconciles the shortfall. Never add stale, weak, duplicate or unverifiable stories merely to reach a number.

### Host-search execution loop — mandatory

Immediately after creating the deterministic plan, run `run_pipeline.py init`, then repeatedly call `run_pipeline.py next`. Execute exactly the returned host action with the Agent's available A/B/C/D capability and persist it using `record-query` or `record-decision`. The runner enforces breadth-first lanes across all rows, schedules the expansion pass for every below-target row, exposes undecided candidates one at a time, and refuses `close-section` while any required lane or candidate decision is missing. `seal-retrieval` replaces a prose completion claim: if it fails, continue with the returned next action. A heartbeat notification, checkpoint or `catch_up_required` result is never a completion condition.

Every `--raw-results` file is a version-1 query receipt containing the exact query, route, status, complete result array and `transport_evidence`. Transport evidence must contain the actual host tool/capability name, an ISO-8601 timestamp with timezone, and either a host invocation ID or a specific explanation that the host does not expose one. The program computes `result_count`; the Agent must not type or estimate it. Every returned URL is persisted before screening, and the receipt hash is copied into the work state and final ledger. A completed zero-result receipt proves only that this one query completed; it never proves the board empty before all required lanes and expansion finish.

Every candidate records one `source_class` from the portable source registry classes and a stable `source_family_id`. `scripts/validate_source_registry.py` checks the real URL hostname against `references/source-registry.json`; an official/Tier-1 claim on an unregistered domain needs same-domain evidence and a specific exception reason. Transport labels such as WebSearch or browser are never source families.

### Deterministic execution plan — mandatory

After capability preflight and before the first board query, read [`references/execution-plan.md`](references/execution-plan.md) and run `python scripts/prepare_run_plan.py --config <normalized-config.json> --report-date <YYYY-MM-DD> --run-id <run-id> --output <workspace>/run-plan-<run-id>.json --config-fingerprint <fingerprint>`. Pass that plan path to `run_state.py start --plan <path>`. The plan is the authoritative queue: every selected board must receive its field, actor, official and business-intersection lanes before rendering begins. Record real progress with `run_state.py checkpoint --state-file <path> --section <section-id>=<checkpoint>` after each completed board batch. When a row has completed all required lanes, candidate review, original-page checks and its continuity decision, record exactly one final outcome using `--section-outcome <section-id>=complete|observed|expanded|business-observation|checked-empty|limited`. Continue immediately with the next unresolved row. `run_state.py` now rejects the HTML-render and delivery phases until every planned row has a final outcome and no pending row remains. A plan is not a background worker and it does not replace host-native search; it prevents an Agent from silently stopping after the first convenient candidate. On resume, use the same plan and pending rows. A reader-facing HTML is prohibited until the plan's selected rows have final evidence-backed outcomes and the normal four delivery gates pass.

A successful bridge result is Mode A discovery, not verification: open the original page through an available direct route before admitting it. If the bridge reports `no_configured_provider`, record it as `skipped-unavailable` and continue to Mode B; do not treat it as a search failure and do not ask the user to create a feed. Never invent an endpoint, API key, connector name, or credential that the host did not expose. An unavailable optional tool is not a run error and must be skipped rather than called again. Split Mode B as B1 personal-cloud automation and B2 ordinary browser/direct webpage: if yz claw actually exposes `yunzhu-browser-automation`, it is a mandatory B1 probe candidate even when `webSearch` is absent; invoke its documented read-only browser open/search action, record the exact status (`working`, `needs-auth`, `view-only`, `disconnected`, `denied`, `failed`, or `skipped-unavailable`) and the opened original page under `run.network_probe.cloud_browser_probe`. A user-authorized cloud computer that the Agent can operate must be operated by the Agent, not delegated back to the user. Probe search API, B1 cloud automation, B2 browser search-page navigation, shell/HTTP client, native HTTP library, RSS/sitemap/listing access, external-feed input, scheduler, and artifact-output capabilities. Record the actual working transport route(s), skipped routes, selected search API (if any), B1/B2 use, and selected retrieval mode in the run audit.

Each route needs its actual status and a specific reason. **A single empty response, timeout, malformed result or zero-URL response from one query is `route-failed`, never `no-candidates`, and may not close a board.** When any native search route has returned candidates for any board in the same run, `limited` is prohibited until that board completes a second discovery pass with changed terms and a changed source family. The required A evidence is an `a_passes` array containing: (a) a broad business query, (b) a board-split query, (c) an official regulator/procurement/listing query, and (d) an original-page opening attempt for every retained candidate. A second pass must use different terms and a different source family; record its actual query, response state and candidate URLs. Only two successful, queryable passes that return no time-qualified, directly verifiable, uniquely assignable event may produce `no-candidates`; retain all rejected candidates and exact reasons. Run `python scripts/validate_route_completion.py <route-evidence> --expected-sections <count>`. A nonzero result blocks both `limited` status and HTML rendering.

### Retry, candidate continuity and non-empty delivery contract — mandatory

1. `route-failed` means the tool did not provide an auditable answer. It is a transport failure, not evidence that a topic is empty. Retry through the next permitted native route or source family before evaluating the topic itself.
2. Create a dated candidate ledger at the first discovery pass. For every candidate retain the query/pass, title, URL, source family, discovered time, displayed publication time, original-page opening result, section assignment and inclusion/rejection reason. On a retry or catch-up, reopen that ledger and continue with unresolved candidates; do not silently discard a usable pool and restart from an empty page.
3. If some sections have verified cards and others do not, render the verified cards normally and close only the genuinely exhausted rows as `checked-empty` or `limited`. A shared search outage must be stated only on the affected rows; it must never erase, downgrade or replace cards already verified for other sections.
4. Before rendering, compare the candidate ledger with the section outcomes. If an opened, time-qualified candidate exists for a section but no specific rejection or included card is recorded, block rendering with `候选未完成复筛`.

### Unknown-section inference and search expansion — mandatory

Before searching any custom, renamed, newly added, or otherwise uncatalogued section, read [`references/unknown-section-retrieval.md`](references/unknown-section-retrieval.md). Create `section-profiles-YYYY-MM-DD.json` for **every** selected section, including known sections, and run `python scripts/validate_section_profiles.py <profile-file> --expected-sections <count>`. Each profile must define the section boundary, inclusion and exclusion rules, keyword tree, actor pool, source-family pool, event types, time-basis policy, and four section-specific query lanes. A broad section name or a single combined query is not a profile. A nonzero validator result blocks the first search query and HTML rendering.

Treat a zero-result first pass as evidence that the current query was too narrow, not that the section is empty. Apply the same expansion used for a mature overseas search: widen from central authorities and central SOEs to local authorities, local SOEs, listed companies, private leaders, counterparties, exchanges/procurement platforms, associations, research bodies, established national media and established vertical media; split the topic into policy/data, project/order, enterprise/product, capital/market, and risk/regulatory event families as applicable. Search each section independently through field, actor, official-record, and business-intersection lanes. If fewer than two qualifying cards survive, run an additional pass with changed terms and at least two changed source families. A section may retain one card when that is all that survives; it may close empty only after all profile lanes and the additional pass are evidenced in the ledger with candidate-specific rejection reasons.

#### Universal overseas-parity execution contract — mandatory for every selected section

The mature overseas search is the minimum reasoning depth for **all** standard, custom, renamed and newly inferred sections, not a special treatment granted only after the user repeatedly asks about one row. Conversation length, user reminders and the order in which sections are discussed must never change retrieval depth. For each row, expand and record three independent dimensions: actor classes (regulator/public institution, central SOE, local SOE, listed/private leader, owner/customer/counterparty, exchange/procurement/association/research), source classes (official/regulatory, company/disclosure, transaction/project platform, national/financial media, vertical/local media), and event families (policy/data, project/order, enterprise/product, capital/market, risk/regulatory, analysis/report). Inapplicable classes may be omitted only when the validated section profile states why; one favored actor, one website or one event wording is never proof of coverage.

When Python is available, initialize the executable loop with `python scripts/run_pipeline.py init --plan <run-plan> --profiles <section-profiles> --reading-receipt <verified-receipt> --work-state <work-state> --output <pipeline-state>`. Every actual search must be recorded through the supervisor's `record-query --raw-results <receipt.json>` with `--source-families-checked`, `--actor-classes-checked` and `--event-families-checked`; every discovered candidate must also carry `source_family_id`, `source_class`, `actor_class` and `event_family`. The program must reject a section that tries to close after one convenient result, lacks three actor/event classes across its completed lanes, misses its planned source-family floor, leaves a candidate undecided, or—when below its card target—has no expansion query covering at least two source families and at least one newly changed family. One genuine qualifying article remains valid after those checks; the contract controls search depth, not an article quota.

The full-package receipt, pipeline state, work state, validated section profiles, raw query receipts, retrieval ledger, source registry, structured editorial model, locked template and HTML are one evidence chain. `authorize-render` compares exact query-receipt hashes and candidate decisions, then binds all inputs by hash. `validate_html.py` invokes the strict ledger validator for every normal dated report; a simplified ledger containing only included cards, a hand-built HTML file or a structure-only validation cannot pass formal delivery. See [`references/unknown-section-retrieval.md`](references/unknown-section-retrieval.md), [`references/retrieval-audit.md`](references/retrieval-audit.md) and [`references/execution-runner.md`](references/execution-runner.md).

### Exact 48-hour time-window gate — mandatory

1. The only reader-facing time ranges are the rolling 24-hour primary window and the immediately preceding 24-hour fallback window. Both boundaries use the actual `Asia/Shanghai` run timestamp to the minute. A date string, crawler time, search-engine recency label, bid deadline, or an event's planned future date must never substitute for the original page's publication/event time.
2. Every candidate must retain `published_at`, `time_basis`, `render_eligible` and `exclusion_reason` in the ledger. A candidate earlier than `run_timestamp - 48 hours`, with an unparseable original date, or with a date known only from a search snippet has `render_eligible:false`. It may remain in the internal candidate ledger, but is prohibited from all reader-facing HTML: full card, `expanded`, `business-observation`, `related-evidence`, 今日重点 and 今日推荐关注.
3. Immediately before rendering run `python scripts/validate_time_window.py retrieval-ledger-YYYY-MM-DD.json --timezone Asia/Shanghai`. A nonzero result blocks HTML rendering, preview, delivery and success marking. The validator must report each violating section, title, source date and reason; do not manually override it to avoid an empty layout.
4. A non-empty page is never a reason to relax the clock. If no candidate survives the 48-hour gate, render only the prescribed checked-empty/limited coverage card for that section. Do not label an old item “扩展观察” to bypass the gate. `expanded` and `business-observation` still require a current, directly verifiable source and never permit an older item.
5. The header must show the exact Shanghai timestamp and both exact ISO-like window boundaries. A report whose metadata omits time-of-day or whose rendered item timestamps cannot be compared to those boundaries is rejected.

1. Never claim that a powered-off computer can execute a local automation. Local schedules trigger only while the relevant local host is available. 3. Exit code `10` means the newest scheduled Shanghai period that is already due has no valid success marker for the current configuration fingerprint. Before today's delivery time it is the preceding scheduled period; after it, it is today. The helper considers only that one target even if the host was closed for many days. Immediately run the normal brief once, naming its HTML and ledger with the returned `local_date`; do not rewrite the news windows to the missed scheduled time, but calculate the rolling 24-hour primary and 24-to-48-hour fallback windows from the actual catch-up run timestamp.

Reopening the host repeatedly cannot duplicate that period, while changing sections, interests, cadence, time, or another fingerprinted setting makes the target period eligible once more.

If the trigger itself arrived materially after the configured local delivery time, record the lateness in the run audit and retain `schedule-unverified` until the host has again supplied both valid timezone evidence and a matching actual `nextRunAt`. Catch-up recovers only the latest due period; it is not proof that the original schedule is healthy and it never backfills a historical series.

Search broad AI events as well as AEC/industrial adoption. Route non-AI software and digital-twin news to `informatization`, physical intelligent-construction technology to `construction-tech`, and financial data-platform news to `fintech`.

If none qualifies there either, first render one real `扩展相关资讯` C-level card; if that remains unavailable, render one real `业务观察` card from a current official statistic, public project/procurement record, authoritative research, association release or established vertical/financial media. Do not use D-level speculation, stale news, anonymous candidates or invented examples. The expanded levels do not count as strict complete coverage or authorize a success marker.

## Write the HTML brief

### Editorial quality and layout gate

### Template lock and delivery circuit breaker — mandatory

The approved daily-brief-template.html is the visual baseline. A run may replace only data-bearing content: dated metadata, selected-board navigation items, evidence cards, recommendations, unlabelled recommendation notes and audit values. It must not replace the application shell, header composition, grouped navigation, search/highlight script, management-map, coverage-audit, or the seven-column audit layout.

1. Do not use a one-off renderer, hand-written fallback HTML, a prior brief as a rendering base, or a reduced page to quickly issue a catch-up. These are delivery failures even if some stories are factual.
2. Any intentional visual/template change requires an explicit user request that identifies the layout change. Record that authorization in the run ledger. Content freshness, a missed schedule, validation trouble or insufficient candidates never authorizes a template change.
3. After the normal ledger and HTML validators pass, run python scripts/verify_delivery_gate.py <artifact> --template assets/daily-brief-template.html. Record its template_sha256 and ok: true under run.delivery_gate in the ledger.
4. If the delivery gate fails, do not attach, link, preview or describe the HTML as a deliverable; do not write a success marker. Report only 版式基线校验失败，未交付, name the failed invariant, and retain the artifact only as an internal rejected draft.
5. The final delivery note may name a report 完成 only when the reading receipt, candidate ledger validator, HTML validator and delivery gate all passed. A documented `checked-empty` or `limited` section is compatible with report completion: it records a completed search and a transparent reader-facing reason, not a fabricated coverage claim. `observed`, `expanded`, `business-observation`, an unsuccessful browser check, or any gate failure still block a success marker; the report may be delivered only if its validators and delivery gate pass and its status is described faithfully.

### Four anti-shortcut hard stops — mandatory

These rules are enforced by the bundled validators and state runner; prose claims, tool summaries and manually typed `passed` values never replace their exit codes.

1. **One section, one evidence trail.** Every selected standard topic and custom interest must execute its own `field`, `actor`, `official`, and `business-intersection` query lanes and write one `query_evidence` record per lane with the exact section-specific query, actual route, status and result count. Related queries may share one batched tool call, but a combined multi-topic query or cluster query never counts for multiple rows.
2. **No early render.** Finding one, three or any other small set of easy-to-verify stories does not close discovery. Every plan row must reach an evidence-backed final outcome, complete its candidate comparison and closure reason, and pass the full-section ledger plus exact-time-window validators before `run_state.py` permits the transition to `html-render`.
3. **No placeholder delivery.** `validate_html.py --allow-placeholders` is restricted to the literal `assets/daily-brief-template.html`. It is forbidden for dated reports, review files, previews and catch-up artifacts. Formal HTML validation always supplies the matching ledger and runs without that flag.
4. **No partial handoff.** Do not attach, link, open, preview or call an artifact complete unless `run_state.py deliver` itself reruns the ledger, time-window, full HTML, editorial and locked-template checks and persists `status: delivered`. Missing section statuses, pending rows, a changed ledger, or any failed gate must return `未交付，待续跑` with the exact remaining rows; it must never return a formal HTML link.

5. **Persist every discovered result.** A query lane's `result_count` must exactly equal its persisted candidate rows. Record every returned URL before screening, then give every candidate an individual inclusion or exclusion decision. A query that reports results but supplies fewer candidate records blocks section closure and HTML rendering.
6. **Use an open source matrix, not a fixed company list.** Read `references/section-source-catalog.md`; check every applicable institutional/source family and run its actor-expansion pass. Named organizations are seeds only. For company-facing boards, include central SOEs, local SOEs, listed/private companies, project owners and counterparties where applicable. Quiet seed sites never prove a board empty.
7. **Keep four dates separate.** Persist original publication time, original update time, explicit event time and retrieval time. Only an explicit event time or original first-publication time can classify the rolling window. Search snippets, repost dates and page update times cannot admit a story. Run 24–48-hour fallback independently only after that board has zero qualified 24-hour items.

### Editorial-depth gate — mandatory

Formal cards must pass a content gate in addition to structural validation. A renderer may not replace the required fields with captions, one-line summaries, generic actions or a missing judgement.

1. Every primary, date-observation, expanded or business-observation card must contain four visible fields: 发生了什么, 为何值得关注, 行动/风险点 and 研判. Each field normally contains at least 45 Chinese characters of substantive prose; a shorter field is allowed only for an explicitly labelled thin-fact observation and must not be selected as 今日重点 or 今日推荐关注.
2. 发生了什么 must state the actor, dated action and at least two available decision facts. 为何值得关注 must identify a board-specific downstream opportunity, cost, risk, competition, compliance or customer decision. 行动/风险点 must identify a concrete next check, decision boundary or delivery risk. 研判 must state a bounded implication and the next observable proof point. Formulaic phrases such as 可作为线索, 持续关注, 继续核验 or 建议关注 alone do not satisfy any field.
3. Before delivery run python scripts/verify_editorial_gate.py <artifact>. Record the result under run.editorial_gate in the ledger. A nonzero result blocks delivery, preview, success marking and any claim that the brief is complete.
4. The editorial gate is a minimum mechanical floor, not a substitute for editorial judgement. If the source cannot support substantive facts, retain it as a candidate or render it as a transparent thin-fact observation; never fabricate detail merely to pass length checks.

Use the supplied `daily-brief-template.html` as an intact application shell. Do not hand-build a reduced header, audit table, search script, or the `management-map` recommendation component. Before delivery, inspect the generated page at desktop width and mobile width when the host can render it; a structurally valid HTML file whose cards, audit rows, recommendations, or header have visibly collapsed is not acceptable.

Every full card is a leadership brief, not a search-result rewrite. Keep the existing fields `发生了什么`、`为何值得关注`、`行动/风险点` and `研判` unchanged, but write substantive prose after each label. `发生了什么` must identify the actor, dated action and at least two concrete decision facts whenever the source supplies them (for example amount, scale, place, project stage, product capability, contract term, counterparty or policy mechanism), normally in two or more complete sentences. `为何值得关注` must use those facts to explain the selected board's opportunity, cost, risk, competition, compliance or customer decision; it must state the relevant downstream scope rather than merely say “值得关注”. `行动/风险点` must name a specific next check, decision boundary or delivery risk. `研判` must state a bounded implication and the next observable proof point. Do not pad thin sources with imagined facts, but do not compress a well-documented source into a caption. Do not use retrieval-process language, generic “持续关注” wording, or a statement about timestamp precision as a `今日信号`.

Before drafting a full card, extract the source's actor, date, event stage, affected object and every available numeric/operational fact. A formal card normally needs at least two such facts, or one fact plus a concrete stage, mechanism or counterparty. If the direct page is too thin, follow the source's announcement, procurement file, company filing, regulator record or credible named report before finalizing; do not compensate with generic analysis. Write the fact paragraph as a coherent management briefing with enough context to stand alone, not a one-sentence caption. The three `今日重点` cards must be genuine primary-window stories.
