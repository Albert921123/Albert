# Generate Daily Industry Brief

Produce a concise, source-linked Chinese morning brief from the user's selected sections. Deliver the brief as a complete `.html` artifact, not Markdown.

## Verify installation and runtime capabilities

1. A ZIP attachment that an Agent can inspect is not automatically a persistent installation. On first use from a newly received package, preserve the complete directory structure, place the `generate-daily-industry-brief` directory in that host's persistent skill directory, and run `python scripts/verify_install.py`. Do not claim installation when the files exist only in an upload cache, temporary extraction directory, or current conversation.
2. On first use on a new host, after a host upgrade, or whenever `webSearch` is unavailable, read `references/runtime-compatibility.md` and select the highest verified retrieval mode that the host actually supports.
3. Search capability is not determined by the tool's brand. Probe available search, browser/fetch, file-input, scheduler, and artifact-output capabilities. Record the selected retrieval mode in the run audit.
4. If neither live search/fetch nor a current verified structured feed is available, do not invent or recall news from model memory. Produce an explicitly limited artifact or fail closed as defined in `references/runtime-compatibility.md`; never label the run complete.

## Create the recurring task

When the configuration includes `create_schedule: true`:

1. Validate it with `scripts/validate_preferences.py`.
2. Before creating the task, run `python scripts/verify_schedule.py --cadence <cadence> --time <HH:MM> --timezone <timezone>`. Use the returned `schedule_contract` as the source of truth.
3. Check for an existing task by stable `subscription_id`, not by time-bearing task name. Update and re-enable it when found; otherwise migrate the single legacy 知讯日报 task or create one task. Immediately use the host's native scheduled-task or Automation action. On hosts that accept natural-language automation requests, execute the request returned as `ZHIXUN_AUTOMATION_REQUEST=`; do not merely display it and never leave a duplicate task.
4. Write all supported values into real scheduler fields: `cadence`, `wall_clock_time`, IANA `timezone`, and the absolute `expected_next_run_local` containing an explicit UTC offset. Prefer a structured local-time schedule. If the host requires Cron, use `cron_expression` together with `cron_timezone`. If it accepts a full RRULE, use the contract value containing `DTSTART;TZID=...`.
5. Codex local Automations may expose only a bare RRULE field. In that adapter only, submit the exact selected local wall-clock hour/minute and cadence (`BYDAY` for weekdays); never substitute the current time, a generated fallback time, or UTC components. Establish that the computer timezone is `Asia/Shanghai`, then verify both the persisted rule and the timezone-aware `nextRunAt`. If either cannot be established, fail closed instead of claiming deployment success.
6. Do not treat a time shown in the task name, prompt, selector, or rule label as proof of scheduling. Obtain both the host's actual `nextRunAt` and its persisted recurrence rule. For Codex, re-read the matching `~/.codex/automations/<task-id>/automation.toml` after the native update; use its `rrule` as the persisted rule and use the Automation record/database only read-only to obtain `nextRunAt`, status, and run history.
7. Verify both values in one command: `python scripts/verify_schedule.py --cadence <cadence> --time <HH:MM> --timezone <timezone> --now <contract-generation-time-if-known> --reported-next-run <nextRunAt> --reported-rrule <persisted-rule>`. Add `--require-timezone-aware-rrule` when the host claims to persist `DTSTART;TZID=...`. A matching `nextRunAt` alone is never sufficient; a nonzero exit means the deployment is wrong.
8. On mismatch, update the same task using the schedule contract, then freshly re-read both `nextRunAt` and the persisted rule and verify again. Retry at most twice. Do not create duplicates. If either value still mismatches, disable the faulty task and report the expected time, actual Shanghai time, persisted rule, and validation issues; never claim successful deployment. If a native host accepts content/status updates but leaves the old recurrence rule unchanged, treat schedule mutation as unsupported. Recreating the task changes its identity: do not delete/recreate automatically unless the user explicitly authorizes that migration.
9. After the task passes schedule verification, persist the exact effective configuration before declaring deployment complete: `python scripts/record_config_state.py --subscription-id <id> --state-dir .zhixun-state --config-file <normalized-config-or-pending-file> --effective-at <selector-submitted-at>`. The saved fingerprint intentionally includes cadence and delivery time as well as sections and custom interests, so any material same-day edit requires a fresh result.
10. Immediately after recording the configuration, run `scripts/check_catchup.py` in the same deployment turn. If the current Shanghai time has passed the newly selected time and the command exits `10`, generate the normal brief once immediately; never wait for tomorrow merely because the scheduler rolled its next occurrence forward. An HTML file or marker produced under a different configuration fingerprint must not suppress this run.
11. Put the normalized JSON in the scheduled prompt and explicitly invoke `$generate-daily-industry-brief` on every run. Require: a rolling 24-hour primary cutoff plus the per-section 24-to-48-hour supplement defined below, concentrated first-party sources, the runtime capability gate and fallback order in `references/runtime-compatibility.md`, the per-section coverage and exclusion audit defined in `references/retrieval-audit.md`, `scripts/validate_html.py` passing before success marking, configuration-fingerprint-aware success marking, and a standalone HTML artifact named `daily-industry-brief-YYYY-MM-DD.html`.
12. Use the host's default task result channel unless `delivery_channel` requests another available connector. If a requested external channel is unavailable or unauthenticated, create the task with the default result channel and explain the remaining connector step.
13. Finish only after the task is enabled, the verified `nextRunAt` matches the contract within 60 seconds, the persisted recurrence rule matches the selected cadence/hour/minute, and the immediate same-day catch-up check has completed. Return the task identifier when exposed, selected sections, expected Shanghai time, actual Shanghai time, recurrence-rule status, catch-up status, and next run. Never invent a task identifier or time.
14. Deployment receipt is mandatory. Whether first-time creation or a section/time edit, once the automation is created or updated and verified, post a deployment receipt in the conversation within the same turn. It must include: the task name, `subscription_id`, cadence (工作日/每天), delivery time and timezone (`Asia/Shanghai`), the expected next run from the `schedule_contract`, the host's actual returned `nextRunAt`, whether the two match within the 60-second tolerance, whether the persisted recurrence rule matches, whether an immediate catch-up was required or completed, and the host task identifier when exposed. On verification failure or missing host capability, report honestly per the rules above; never fabricate success.
15. If the host exposes no Automation creation action, no actual next-run value, or no readable persisted recurrence/schedule listing, do not claim success. Return the prepared task name, schedule contract, and prompt, and state precisely which host field could not be created or verified.

## Handle an offline or missed local run

1. Never claim that a powered-off computer can execute a local automation. Local schedules trigger only while the relevant local host is available. Recommend the host's cloud or always-on scheduler (such as WorkBuddy Cloud, the operating system's Task Scheduler, or a cron daemon) when the brief must run at the exact wall-clock time regardless of the computer state.
2. Before any catch-up decision, require a current configuration state written by `scripts/record_config_state.py`. When `missed_run_policy` is `catch_up_same_day`, ask the host to attach a resume/startup/agent-launch trigger only if that trigger is actually supported. On each such trigger, run `python scripts/check_catchup.py --cadence <cadence> --time <HH:MM> --timezone <timezone> --subscription-id <id> --state-dir .zhixun-state --output-dir .`.
3. Exit code `10` means the current Shanghai date is scheduled, the wall-clock time has passed, and no valid success marker exists for the current configuration fingerprint. This includes a same-day HTML or marker created before a material settings change. Immediately run the normal brief once. Do not rewrite the windows to the missed scheduled time; calculate the 24-hour primary and 24-to-48-hour fallback windows from the actual catch-up run timestamp.
4. After a complete-coverage HTML artifact is fully written and `scripts/validate_html.py` has passed, run `python scripts/mark_success.py --subscription-id <id> --timezone <timezone> --state-dir .zhixun-state --html-file <artifact>`. The helper reads `current-config-<id>.json` and stores its fingerprint in the success marker. If validation fails or any selected section remains `limited` under `references/retrieval-audit.md`, label the artifact and delivery as partial and do not write the success marker, so a same-day retry remains possible. Do not mark failures as success.
5. Exit code `0` means no catch-up. Deduplicate by subscription ID, Shanghai local date, and current configuration fingerprint. Reopening the host repeatedly cannot duplicate the same configuration, while changing sections, interests, cadence, time, or another fingerprinted setting makes the same date eligible once more.
6. Treat legacy HTML files and markers without a fingerprint as valid only when no current configuration state exists. Once `current-config-<id>.json` exists, a missing or mismatched marker fingerprint is stale and must not suppress a catch-up.
7. If the host exposes neither a recovery trigger nor a cloud scheduler, explain that automatic open-computer catch-up cannot be guaranteed. The user can still type `补发今天的知讯日报`, which must run the same fingerprint-aware check. Deployment itself must still run the immediate check from `Create the recurring task`, even when no recovery trigger exists.

## Collect current information

1. Determine the exact run timestamp in `timezone`, defaulting to `Asia/Shanghai`. Set `primary_cutoff = run timestamp - 24 hours` and `fallback_cutoff = run timestamp - 48 hours`. The fallback segment is `[fallback_cutoff, primary_cutoff)`; it is not a replacement for the primary window.
2. Read `references/topics.md` for the selected sections only, then read `references/section-source-catalog.md`, `references/discovery-source-ladder.md`, `references/source-map.md`, `references/retrieval-audit.md`, and `references/retrieval-routing.md`; on a new host or when full search is unavailable also read `references/runtime-compatibility.md` before retrieval.
3. Create one coverage-ledger row for every selected standard section and every custom interest before issuing searches. Give every row a field-first breadth pass and a source/actor pass before deep-verifying any section; then use the construction/business intersection lane for ranking and cross-section evidence. A global construction-news query does not count as coverage for all rows, and a construction-only query cannot prove a broad adjacent field empty.
4. Select the highest supported retrieval mode from `references/runtime-compatibility.md`: Mode A search plus direct-page verification; Mode B direct official-source/RSS/browser retrieval; Mode C a current structured JSON feed that passes `scripts/validate_news_input.py`; or Mode D explicitly limited/offline output. Execute the adaptive finding and evidence-based empty-section checks in `references/retrieval-audit.md`, and use the mandatory event-level route ladder in `references/retrieval-routing.md`. Separate discovery from verification: search Tier 1 families and the broad Chinese discovery pool in `references/discovery-source-ladder.md`; then verify each event with the closest accessible evidence. An established Tier 2 page may be the reader-facing citation for an ordinary event when it names the underlying actor/record, supplies a qualifying date, and is labeled `T2权威转述`; material or disputed claims still require an official record or two independent credible sources. A successful zero-result query or a current official listing whose newest entry is outside the window is valid coverage evidence; it is not a retrieval failure.
5. A section with verified qualifying items in the primary window is `complete` once it meets the finding threshold; do not require the broader quietness threshold merely to retain valid news. When a section has no qualifying primary-window item and its required query plus official-source check both executed successfully, treat the primary window as checked-empty and search the fallback segment from 24 to 48 hours ago. Include qualifying fallback items with an explicit `48小时补充` label. Do not mix fallback items into a section that already has a qualifying primary-window item. Retry only a path that failed; mark `limited` only after that failed path remains unavailable, never merely because the section returned zero candidates.
6. Include an item only when its original publication timestamp or the underlying event timestamp is within `[fallback_cutoff, run timestamp]`, then classify it as `primary` when it falls in `[primary_cutoff, run timestamp]` or `fallback` when it falls in `[fallback_cutoff, primary_cutoff)`. A fresh repost of an older event does not qualify. A date-only page on a window-boundary date is ambiguous and must be excluded unless metadata or the underlying event supplies a qualifying time. Apply the section-level fallback gate before rendering any `fallback` item.
7. Never widen beyond 48 hours to 72 hours or seven days, including weekends and quiet news days. Report a checked-empty section instead of backfilling material older than the fallback cutoff.
8. Open every plausible candidate through at least one accessible evidence route. Confirm the title, qualifying publication/event timestamp, core fact, publisher, and direct URL. Failure of the first URL is a route failure, not an item failure: continue through the official alternate endpoint, event counterparty/registry, and qualifying Tier 2 routes in `references/retrieval-routing.md` before excluding it.
9. Exclude duplicate syndications, pure opinion without a new event, clickbait, unverified claims, and undated pages. Do not exclude an otherwise qualifying event merely because its primary business value belongs to another selected section. Render it once as the primary story and add a compact source-linked `关联资讯` card in every other genuinely relevant selected standard section; record `related_count` separately and never count those cards as additional stories. A related card never satisfies a section's own breadth or main-story search target. For a custom-interest section, a related card is supplementary only and can never be its sole rendered evidence or make the row `complete`.
10. Keep at most `max_items_per_topic` items per section, defaulting to twenty and never exceeding twenty. This is a ceiling, not a quota. For a high-output field with fewer than two qualifying main stories, run the additional discovery pass in `references/retrieval-audit.md` before finalizing; retain 2–3 strong non-duplicate items when available and report genuine scarcity honestly. Rank by exact section relevance, source authority, freshness and decision value; use alignment with `industry_scope` as a ranking bonus rather than a universal filter. Before writing, run the source-diversity checks in `references/retrieval-audit.md`; do not let convenience mirrors or one disclosure portal dominate the brief when equivalent independent sources are available.
11. For `leadership`, verify the speaker's current role from an official source and capture the occasion, event timestamp, core argument, and business implication. Prefer a faithful paraphrase; use only a short direct quote when wording is material.
12. For `fintech`, follow the dedicated financial-services and data-tech watchlist in `references/source-map.md` and `references/section-source-catalog.md`. Search regulation, products, enterprise customers, transactions, partnerships, operating results and risks across B2B/industrial financial technology. Prefer AEC and industrial-chain implications, but do not reject a valid fresh sector event solely because it lacks a construction customer. Exclude consumer promotions, lifestyle finance and generic technology publicity with no financial/data-platform implication.
13. For `digital`, collect AI news only. Require AI capability, product, model, agent, compute/data infrastructure, governance or meaningful adoption to be the core novelty. Search broad AI events as well as AEC/industrial adoption. Route non-AI software and digital-twin news to `informatization`, physical intelligent-construction technology to `construction-tech`, and financial data-platform news to `fintech`.
14. For each `custom_interests` value, derive field, source/actor and business-intersection cues from the exact phrase, search it as an independent broad section, and apply the same 24-hour-primary/48-hour-fallback, Tier 1-first, deduplication, coverage-ledger, and `max_items_per_topic` rules. Keep the user's exact label as the section title. Treat the custom field itself as sufficient scope unless the user explicitly narrows it; use the configured construction/AEC ecosystem only to rank and explain items. For every custom row, execute four mandatory lanes: exact-field events; named sources/actors; official/regulatory/registry/project records; and business/AEC intersections. If zero or one main story qualifies, run one additional national/vertical/mirror discovery pass before finalizing. Old HTML, replay files, or another section's candidate pool may suggest leads but cannot satisfy a newly added custom row's own lanes. For example, `半导体` covers policy, chips, fabs, equipment, materials, EDA, packaging/testing, capital expenditure, financing, M&A and company operations, not only semiconductor-factory construction.
15. Route at least one directly relevant qualifying event to each custom-interest section as a formal main story whenever such an event exists. If the same event also fits a standard section, the custom section gets the main story when it is the only qualifying custom result and the standard section receives the `关联资讯` card; do not leave the custom row related-only. If no primary-window main story qualifies after the mandatory lanes, complete the custom row's 24-to-48-hour fallback search. If none qualifies there either, render `checked-empty` or `limited` honestly instead of padding with a weak relationship.
16. Before writing, reconcile ledger totals: every selected section must be `complete`, `checked-empty`, or `limited`; primary included counts must equal rendered stories; related counts must equal rendered `关联资讯` cards; excluded counts must equal the recorded reason totals; and final source-domain counts must pass the diversity audit or carry a specific exception. If any row is missing, a custom row is related-only, a related-only standard row skipped its own discovery passes, or a candidate was dropped only because its first URL failed, continue the applicable alternate route rather than silently producing a thin or empty section.
